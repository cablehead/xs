A `last:n` topic no longer gets slower as it grows, many frames can be appended in one request, and the content store finally deletes what no frame uses.

| per append, a topic held at `n` by `last:n` | 0.15.1 | 0.16.0 |
|---|---|---|
| index entries read, `n` = 50,000 | 50,001 | 1 |
| gc work, `n` = 50,000 | 17.66 ms | 0.14 us |
| index entries read, `n` = 5,000,000 | 5,000,001 | 1 |
| gc work, `n` = 5,000,000 | 759.3 ms | 0.13 us |

## `last:n` keeps a count per topic (#181)

The store keeps a live frame count for each `last:n` topic, so an append that takes a topic over `n` removes the oldest frame in its own commit, instead of a scan back through the topic. A topic is counted once, the first time a `last:n` frame lands on it; a store from 0.15 opens and counts its topics as they are used. Plain appends with no `last:n` measure within about 2% of 0.15.1.

A topic is trimmed by the append that carries `last:n`, not continuously: between such appends it can grow, and the next one brings it back to `n`. The docs now say so.

## `POST /append-batch` (#158)

Appends every line of an NDJSON body as one atomic run: consecutive ids, nothing else between them, and a reader sees all of them or none.

```sh
printf '%s\n' \
    '{"topic":"clip.add","meta":{"n":1}}' \
    '{"topic":"clip.add","meta":{"n":2},"ttl":"last:100"}' |
  curl --unix-socket ./store/sock --data-binary @- http://localhost/append-batch
```

A line holds `topic`, and optionally `meta`, `ttl` and `hash` (content already stored with `POST /cas`). A malformed line, an invalid topic, or more than 1024 frames returns 400 and stores nothing. Over one connection, batches of 1000 reach about 397,000 frames a second, against about 29,700 for one frame per `POST /append/{topic}`.

## Unused content is deleted (#184)

Removing or trimming a frame used to leave its content in the CAS forever, as did every ephemeral frame's content. Now the server deletes content no stored frame points at, once it is an hour old: once as it starts, and on `POST /gc`, which answers with what it did.

```sh
$ curl --unix-socket ./store/sock -X POST http://localhost/gc
{"in_use":18,"recent":87,"deleted":28720,"bytes_freed":10700000000}
```

## Breaking

- **Nushell 0.117.0** (#178). xs embeds Nushell 0.117.0, and Datastar moves to 1.0.5. Code that embeds xs needs `nu-*` 0.117.
- **Content only a client knows about is deleted** (#184). Content stored with `POST /cas` and not pointed at by any frame is deleted an hour after it was written, at the next server start or `POST /gc`. Point a frame at content you want to keep.
- **Don't run 0.15 on a store after 0.16** (#181). 0.15 does not know about the per-topic counts, so its appends and trims leave them stale. If a count then reads high, 0.16 trims frames it should keep.

## Fixes

- An idle duplex service no longer wakes 100 times a second. Its input read waits for the next frame instead of polling every 10 ms (#182).
- One-shot commands flush stdout before exiting, so their output is not lost (#179).
